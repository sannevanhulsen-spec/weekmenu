# Weekmenu Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A free phone PWA. It suggests dinner recipes based on this week's offers at AH, Jumbo, Aldi and Lidl, shows price and nutrition per recipe, builds one shopping list, and picks the cheapest single store or pair of stores.

**Architecture:**
- One public GitHub repo, served by GitHub Pages: a static React PWA plus static JSON data (recipes, ingredient catalogue, NEVO subset, prices).
- A daily GitHub Actions job runs a Node fetcher that reads Jumbo and Aldi public pages (robots.txt-compliant) and commits `data/prices/latest.json`.
- **AH and Lidl prices are entered by hand** by the owner (decision of 2026-11-15, see the spec §7). There is no AH or Lidl fetcher.
- All pricing, comparison, nutrition and suggestion logic is pure TypeScript in `shared/`, used by both the app and the fetcher.
- All personal state lives in IndexedDB on the phone.

**Tech Stack:**
- Node 24 (`.nvmrc` = `24`, same as HuishoudSaven) and TypeScript.
- React 19 + Vite 7 + Tailwind CSS v4 + `vite-plugin-pwa`.
- `idb` for IndexedDB.
- Vitest + @testing-library/react + `fake-indexeddb` for tests.
- GitHub Actions + GitHub Pages.

**Spec:** `docs/superpowers/specs/2026-11-14-weekmenu-design.md`. Read it first.

## Global Constraints

- €0/month: no paid APIs, proxies, hosting or AI at runtime.
- UI text in Dutch. Code, identifiers and file names in English.
- Household is 2 persons. Recipe quantities are stored for 2 persons; one portion is half.
- Stores: `ah`, `jumbo`, `aldi`, `lidl`. A shopping list uses at most 2 stores.
- Fetchers only request URLs that the store's robots.txt allows, at most 2 requests per second.
- AH and Lidl: manual prices only. A manual price counts as real and stores `enteredAt`.
- Multi-buy offers count ("1+1 gratis", "2e halve prijs", staffels).
- Estimated prices are always shown with the prefix `~`. An estimated price never beats a real price. A user-entered price counts as real.
- NEVO values are stored unchanged per 100 g. The app shows the attribution exactly as: `NEVO-online versie 2025/9.0, RIVM, Bilthoven`.
- Recipes must not be copied from Allerhande or any other site. They are original text written during the build.
- No personal data in the repo.
- Build rules from `C:\Projects\HuishoudSaven\basis regels.md`: simplest first, no speculative abstractions, every task ends in a verifiable check.

## Review Focus

1. **An offer that ends during the planning week.** An offer with `validUntil` before today must not be applied. `validUntil` is inclusive. Pinned in Task 3.
2. **Too few recipes left** after filters and "Lust ik niet". The app shows the recipes that remain plus the text `Minder voorstellen door je filters`. It must not crash or repeat a recipe. Pinned in Task 6.
3. **A store's scrape fails.** That store keeps its previous data, marked `stale: true`, and the app shows `<Winkel>: prijzen van <datum>`. Pinned in Task 8.
4. **An ingredient with no price at any store.** It is left out of the totals and counted as `n items zonder prijs`. It is never priced at €0. Pinned in Task 4.
5. **Piece-based ingredients versus weight-based products.** Example: 2 onions in the recipe, onions sold per kg. Convert with `gramsPerPiece`. If the units cannot be converted, there is no match; a wrong price is worse than no price. Pinned in Task 3 and Task 7.

### Task 3: Units, offers and purchase cost

**Files:**
- Create: `shared/pricing.ts`
- Test: `tests/shared/pricing.test.ts`

**Interfaces:**
- Consumes: the types from Task 2.
- Produces:
  - `toProductUnits(amount: number, ing: Ingredient, product: Product): number | null`. Converts a recipe amount into the product's unit; `null` if it cannot.
  - `activeOffer(p: Product, today: string): Product['offer'] | undefined`
  - `purchase(p: Product, needed: number, today: string): { packs: number; cost: number; hint?: { packs: number; cost: number } }`. `needed` is in product units.
  - `usedCost(p: Product, needed: number, today: string): number`. The cost of only the used amount, at the effective unit price; used on recipe cards (spec §8.6).

- [ ] **Step 1: Write the failing tests.**
  - `toProductUnits`:
    - 2 stuk ui, gramsPerPiece 100, product 1000 g → `200`.
    - stuk ingredient without gramsPerPiece, product in g → `null`.
    - g ingredient, product in stuk → `null`.
  - `activeOffer` with validUntil `2026-11-16`:
    - on `2026-11-16` → the offer is returned;
    - on `2026-11-17` → `undefined`;
    - before validFrom → `undefined`.
  - `purchase`, no offer: needed 600 g, pack 500 g at €2.00 → `{ packs: 2, cost: 4.00 }`.
  - `purchase`, `multi` 1+1 (buy 2, pay 1): needed 400 g, pack 500 g at €3.32 → `packs: 1, cost: 3.32`, with `hint: { packs: 2, cost: 3.32 }`. The hint means taking 2 costs the same and gives more.
  - Hint rule: a hint appears only when buying extra packs to reach the offer threshold gives a lower price per unit and costs at most €1.00 more than the minimum purchase.
  - `purchase`, `bundle` 2 voor €5, price €2.99, needed 1 pack → `cost 2.99`, `hint { packs: 2, cost: 5 }`.
  - `purchase`, `price` offer €1.49 replaces €2.19 → `cost 1.49` per pack.
  - `usedCost`: 200 g from a 500 g pack at €2.00 → `0.80`. Under 1+1 the effective unit price is halved → `0.40`.
- [ ] **Step 2: Run the tests.**
  - Run: `npx vitest run tests/shared/pricing.test.ts`
  - Expected: FAIL.
- [ ] **Step 3: Implement.**
  - Multi-buy cost for n packs:
    - deal groups = `floor(n / buy)`;
    - cost = groups × pay × price + (n mod buy) × price.
  - Bundle cost works the same way with `count` and `price`.
  - Effective unit price = cost of one full deal group divided by its total amount.
- [ ] **Step 4: Run the tests again.**
  - Expected: PASS.
- [ ] **Step 5: Commit**
  - `git commit -m "feat(shared): units, offers and purchase cost"`

- Create: `app/src/screens/Suggestions.tsx`, `app/src/screens/RecipeDetail.tsx`
- Test: `tests/app/suggestions.test.tsx`

**Interfaces:**
- Consumes: `suggest` and `recipePrice` (Task 6), `nutritionPerPortion` (Task 2), and `loadState`/`saveState` (Task 9).

**Behaviour (spec §8.5):**
- **Nieuw weekmenu** starts a new `Week`.
- The screen shows 12 suggestions. Each card shows: title, minutes, price for 2 (prefixed `~` when estimated), kcal and protein per portion, and an `Aanbieding` badge when offerShare > 0.
- Card buttons:
  - **Kies** adds the recipe to `chosen`.
  - **Wissel** adds it to `swappedAway` and shows the next suggestion in its place.
  - **Lust ik niet** adds it to `dislikedRecipes`.
- Detail view:
  - all six nutrients per portion, rounded to whole numbers, salt to 1 decimal;
  - the ingredients for 2 persons, each with its own **Lust ik niet**;
  - the steps;
  - a **Lekker** (favourite) toggle.
- A filter bar sits at the top and its settings persist.
- When fewer than 12 suggestions are left, the screen shows `Minder voorstellen door je filters`.

- [ ] **Step 1: Write the failing tests** (Testing Library, with fixture data):
  - After **Lust ik niet** on a card, that recipe is gone and stays gone after a reload of the state.
  - **Wissel** replaces the card with a different recipe.
  - An ingredient-level **Lust ik niet** removes every card that uses that ingredient.
  - Turning on the `Veel eiwit` filter leaves only cards with ≥ 30 g protein.
  - An estimated price renders with a leading `~`.
